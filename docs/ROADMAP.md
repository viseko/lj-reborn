# LJ Reborn — дорожная карта

Формат работы: я объясняю и ревьюю, весь код и конфиги пишешь ты. Отмечай `[x]`, когда часть пройдена и отревьюена.

## Стек

- **Backend:** Fastify + TypeScript, Prisma, PostgreSQL 16, JWT (access в httpOnly-cookie + refresh), node-cron
- **Frontend:** Next.js 16 (App Router), React, Zustand, SCSS-модули, кастомный pointer-based DnD, тёмная/светлая темы, методология Feature-Sliced Design, Storybook для компонентов
- **Качество:** Vitest, Playwright, ESLint (flat config), Stylelint, Prettier, автоформат при сохранении, husky + lint-staged + commitlint, Conventional Commits, GitHub Actions
- **Монорепо:** pnpm-воркспейсы, `backend/` и `frontend/`, общий `pnpm-lock.yaml` в корне

## Потом (после авторизации)

Посты, комментарии, теги, друзья, ленты подписок, сообщества, приватные записи, pointer-based drag-n-drop.

Первая задача при появлении защищённых эндпоинтов (из 6.9): `apiFetch` на 401 → `refreshTokens()` → один повтор запроса; не применять к `/auth/*` (там 401 = «неверный пароль», не «токен истёк»); механизм уведомления стора о неудачном refresh из `shared` (колбэк/событие — `shared` не импортирует `entities`). Плюс открытый вопрос: две вкладки со старым refresh после ротации попадают в ветку массового отзыва — нужна координация между вкладками (например, `BroadcastChannel`/`navigator.locks`) или окно терпимости на бэке.

При первой новой миграции (из 7.2): `globalSetup` в Playwright — один раз перед всем прогоном `prisma migrate reset --force` для `lj_e2e` (чистая база + схема синхронна с миграциями; между тестами не чистим — воркеры параллельны). В CI не нужно — там свежий контейнер Postgres на каждый прогон.

**Очередь после 7.3:** (1) обновление зависимостей → (2) пароль в скрытой форме → (3) полиморфный `Button`. Обновление первым: сборка падает на первом запуске (тормозит каждый прогон e2e), критичные уязвимости, и дальше чиним уже на итоговой версии Next. `pnpm audit` (2026-10-28): 28 уязвимостей — `next` 16.4.0 (critical RCE в Image Optimization, high DoS; исправлено в ≥16.4.1), `zod` (high, память при огромном вводе — валидирует тела запросов бэка), `storybook`/`@storybook/addon-vitest` (critical, dev-сервер), `fastify`, `fast-jwt`, `fast-uri`, `@vitest/mocker` и др. Коммиты раздельно: сначала `next`, потом рантайм (`zod`, бэк), потом dev-инструменты.

**(2)** (найдено учеником в 7.3): с `cacheComponents` Next 16 при клиентской навигации прячет предыдущую страницу через React `<Activity>`, сохраняя состояние → после входа скрытая форма с логином и **паролем** (`value` в DOM) остаётся на странице; после выхода и перехода на `/login` форма заполнена старыми данными (общий компьютер). Касается входа, регистрации, сброса пароля. Сначала падающий e2e (вход через UI → выход → клик «Войти» → поля пустые), потом исправление.

Из 7.2 (найдено при написании локаторов): в хедере гостевая ссылка «Зарегистрироваться» — `<Link><Button>` (интерактивный внутри интерактивного, невалидный HTML) → ссылка, стилизованная как кнопка. Выбран подход (7.3): полиморфный `Button` (проп `as`/паттерн `asChild`) — стили кнопки остаются в одном месте; типизация пропсов через дженерики. **(3) в очереди после 7.3.**

Из 7.3: хедер авторизации отдаётся потоком (`Suspense` + `cacheComponents`) → до прихода второго куска на месте блока пустота (pop-in «пусто → логин», не «гость → логин»). Проверить на медленной сети (throttling в DevTools); если заметно — зарезервировать место под блок; блокирующий рендер искать только если это не поможет.

## Решения

- Репозиторий на GitHub (публичный): `github.com/viseko/lj-reborn`, CI на GitHub Actions
- Деплой: фронтенд на Vercel; бэкенд (Fastify + `node-cron`) отдельным долгоживущим процессом (Render/Railway, позже возможно VPS); база во внешнем Postgres (например, Neon)
- Фронт и бэк на разных доменах: учесть в cookie (`SameSite`, `Domain`) и CORS в модуле 3
- Домены в проде: `site.com` (фронт) и `api.site.com` (бэк) — поддомены одного домена, один "сайт" для `SameSite=Lax`. К деплою: `access_token` ставить с `domain: ".site.com"` (через env, например `COOKIE_DOMAIN`, локально без него), иначе middleware и серверные компоненты Next.js не увидят сессию; `refresh_token` оставить привязанным к `api.site.com` (фронтенду он не нужен). Прокси через `rewrites` при такой схеме не нужен
- Хедер без моргания: клиентские варианты (пустой слот, плавное появление) отвергнуты — до ответа `/auth/me` в первом кадре либо неверный блок, либо пустота. Решение — серверный рендер состояния авторизации в `Header` (пункт 6.8). Локально работает сразу (cookie привязаны к домену, не к порту — `localhost:3000` видит cookie от `localhost:4000`); в проде требует `COOKIE_DOMAIN` (см. выше)
- E2E «без моргания» (7.3): тест с `javaScriptEnabled: false` отвергнут — с `cacheComponents` хедер авторизации приходит потоком, и на место fallback его переставляет inline-скрипт React, без JS блок остаётся скрытым. Требование «видно без JS» потребовало бы блокирующего рендера против устройства фреймворка. Проверяем то, что реально защищает от моргания: сервер не рисует гостевое состояние (сырой HTML: логин текстом в разметке, нет `href="/login"`). Логин ищем как `>login<` — пропсы серверного компонента для клиентского сериализуются в HTML (`self.__next_f.push`), простой поиск логина проходит всегда
